# 工单管理总体设计：产品、版本、项目分支与统一代码准备

日期：2026-11-13。状态：首期试用版已实现，完整目标按下列实施边界分阶段推进。

本文是工单功能的主方案；[工单小队设计](./work-order-squad-design.zh.md)是执行组织补充。需求来自用户原始 `docs/工单管理设计.md`。本文保留完整目标架构，不代表后续各节的所有交互均已上线；实际配置与验收以[首期试用指南](./work-order-pilot-guide.zh.md)为准，不复制原文中的凭据。

## 当前实施边界

- 已实现工作台工单处理、后台独立工单维护、成员按负责人隔离、管理员下派、手工导入和 MIS 手动分页只读同步。
- 已实现产品英文标识、版本默认主仓库、可配置模块落盘目录、明确分支、备注和按产品选择具体依赖版本；服务镜像、原 CI 地址和 Compose 独立放在可选页签，不作为代码维护前置。
- 依赖页提供明确的添加、变更和移除操作，可就地新增依赖产品与版本；支持先登记依赖再补齐仓库，但执行计划必须完成所有版本的模块配置。项目右侧提供共享版本模块和依赖的维护入口。
- 已实现全局共享的后台项目管理：产品、版本、模块、依赖和客户项目分支由所有工作区复用，无需选择工作区。客户项目绑定默认产品版本、展开全部依赖模块，未覆盖模块继承版本基线。工单转任务时确认并登记/复用客户项目，无需重复导入；临时分支可明确选择保存为共享项目配置。历史版本映射保留。
- 后台项目可独立新增、改名、维护版本分支和删除，不依赖工单登记。删除需确认并清理该项目所有历史分支配置；任何工单仍引用时拒绝删除，不破坏已确认任务的关联。
- 已实现完整代码计划、转原生搁置任务、冻结计划、子任务继承，以及新版运行时按产品/模块统一准备仓库和记录实际提交。
- 已实现一个规范 KB 总目录和产品/版本/模块/分支的目录命名规则；尚未自动创建、下载或上传规范文档。
- 尚未实现自动 GitLab 扫描、版本配置复制、项目远程分支自动创建、自动收集 CI 镜像、组合环境自动部署和 MIS 写回。仓库与原 CI 均不改造。
- 尚未自动创建工单小队，不改已有开发小队。系统管理员通过既有部署白名单进入工单维护，可显式选择工作区管理；普通成员与工作区管理员仍受本工作区权限约束。
- 默认界面为简体中文；保留用户手动保存的其他语言选择。

## 1. 核心结论

不是先建一个会修 Bug 的小队，而是先建立可靠的产品代码档案：

```text
后台维护
  产品 -> 模块 -> 仓库
       -> 产品版本 -> 各模块仓库和基线分支
                   -> 依赖的其他产品版本
  客户项目 -> 使用的产品版本 -> 各模块项目分支
                            -> 未定制模块继承版本基线
  一个知识库总目录 -> 产品 -> 版本 -> 模块 -> 分支规范文档
                            |
灵工工作台“工单”             |
  读 MIS 原单 -> 自动匹配上述档案 -> 研发确认/调整分支和描述
  -> 一次生成完整代码清单 -> 转任务并启动专属工单小队
  -> 一个根目录内准备主产品与全部声明依赖的模块代码
  -> 下载已有规范，缺失则生成并回传知识库
  -> 定位修复 -> 独立验证 -> 提交 -> 各仓库原有 CI
  -> 汇总产出镜像 -> 组合运行环境 -> 人工验收
```

后台数据决定取什么代码，统一代码准备能力保证代码实际落地，小队负责在准备好的上下文中解决问题。三者缺一不可，不能只依靠提示词让智能体自行猜仓库、分支和依赖。

## 3. 后台页面如何调整

### 3.1 保留“系统管理 -> 产品管理”

保留现有入口及左侧产品列表，不再另建一套重复的产品基础信息。项目维护独立于产品管理；产品模块默认库可在后续扩展：

```text
系统管理 / 产品管理

产品列表       ECM                         [编辑产品]
ECM            [版本管理] [模块仓库（后续）]
Search
Inbiz
V9
```

全局操作提供“批量导入”和“GitLab 梳理”；版本管理仍是默认标签。普通成员在工单中可读取有权使用的档案，但不能因为能接单就修改全局产品配置。

产品、版本、模块、依赖和客户项目分支都是部署级共享档案，不属于某个工作区。独立“项目管理”直接选择客户项目；后台和各工作区工单使用同一份配置。后台维护沿用系统管理员白名单；普通成员可读取共享档案，通过本人已分派工单登记或确认项目，只有明确选择保存分支时才写回共享配置。共享档案不包含凭据，也不授予其他工作区的工单、运行时或仓库访问权限。

### 3.2 “模块仓库”标签

产品下维护稳定模块，不把整个产品限制成一个仓库：

| 模块 | 模块标识/目录名 | 默认仓库 | 仓库内路径 | 备注 |
| --- | --- | --- | --- | --- |
| 核心服务 | `core` | 选择已有仓库或粘贴 URL | `.` | 构建方式、历史说明 |
| 其他模块 | 人工确认的稳定短名 | 可与其他模块相同或不同 | 可填写子目录 | 可选 |

支持新增、行内编辑、批量粘贴、连通性检查和停用。已有历史版本引用的模块/仓库不能直接硬删；停用后不供新版本选择，历史记录保留。

仓库身份与访问凭据分离：后台档案保存 GitLab 实例、项目身份和规范 URL；工作区的 GitLab 连接及运行时认证负责访问，不在全局档案中放令牌。

这里的仓库是录入新版本的默认值，不是所有历史版本的实时引用。修改模块默认仓库只影响后续录入，不改变已有版本的代码来源。

### 3.3 “版本管理”标签

保留版本名称、备注、启用状态，并增加代码配置状态、模块数、依赖数。已有知识库字段保留原语义和旧功能使用方式；工单规范不再逐版本选择目录，统一从系统设置的一个总目录自动归档。版本基础信息编辑仍可快速完成；点击“配置代码”打开版本详情，不把所有配置挤进当前小弹窗。

当前试用版提供“模块代码”“依赖产品与版本”“构建与部署（可选）”三个页签，默认只维护代码。空配置自动提供标识 `main` 的“主仓库”，填写仓库和分支即可，无其他仓库时不用新增模块。产品编辑维护全局唯一英文标识，代码目录预览使用该标识而非产品 ID。“知识规范”状态和版本级“完整代码预览”为后续扩展，当前在工单确认时查看完整代码计划。

**模块代码**

| 模块 | 该版本仓库 | 版本基线分支/tag | 仓库内路径 | 本地相对目录 | 校验结果 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| 主仓库 | 显式保存当前版本的仓库 | 从远程选择或手填 | 留空 | `main`（默认） | 存在/未验证/不存在/无权限 | 可选 |

落盘目录是该版本目录内自动创建的相对目录，留空取模块标识；仓库内路径仅用于已存在的源码子目录，折叠为高级项。模块目录不得重复或嵌套，避免把其他 Git 仓库放进主仓库。

操作包括“从产品模块填充”“复制上一版本”“批量设置分支”“检查代码配置”。复制后新版本状态为待校验，不能因上一版本可用就认定新版本可用。

每个版本明确有哪些模块。老版本没有的新模块不自动加进去；每个启用模块都进入完整代码清单，不让 AI 因当前看起来无关就漏拉。

历史版本继续使用各自已有仓库、构建入口和 CI 模式。版本模块可登记现有 CI 的查询方式、产物位置及镜像/服务映射，不要求修改流水线文件、构建脚本、发布规则或镜像命名。一个仓库产出多个服务镜像时逐项登记，不能假定一个模块只对应一个镜像。

**版本依赖**

| 依赖产品 | 依赖版本 | 纳入模块 | 备注 |
| --- | --- | --- | --- |
| Search | 选择已存在的真实版本 | 默认全部，可显式选模块 | 兼容原因、调用关系 |

必须指向具体版本，不使用“最新版”。允许不同产品版本相互依赖，展开时按版本 ID 去重，遇到已访问版本不再重复展开；添加时检查重复和版本冲突。支持查看展开后的依赖树。依赖版本未配置完整时，父版本也显示待补齐。

**知识规范**

只读展示总目录下自动推导的产品/版本路径，以及各模块、分支的规范状态、适用基线、生成时间和待更新原因，不再提供逐版本目录选择器。总目录只在系统设置中选一次。提供“查看文档”“准备知识”；生成需要运行时和授权，普通保存不建目录、不唤醒智能体。

**完整代码预览**

展开当前产品及递归依赖，展示所有模块、实际仓库、版本基线、路径和冲突。预览只读，不 clone、不建分支；用于确认“这个版本到底由哪些代码组成”。

配置状态独立于版本原有 `enabled`：未配置、待校验、可用于工单、存在阻塞。旧版本仍可用于原有产品版本选择；只有启动需要统一代码准备的工单时，才要求档案完整。

### 3.4 独立“项目管理”

当前入口为“系统管理 -> 项目管理”，不放在产品版本代码配置或工单执行设置里。客户业务项目使用全局 `customer_project` 档案，与工作区内承载任务的 `project` 分开；保存默认产品版本，分支按客户项目、版本和模块分别维护。迁移保留原客户项目 ID，不删除原工作区项目或搬移任务。

首次处理工单时，确认来源项目名称或选择已有项目，再确认产品版本和实际分支；确认后进入维护列表。后续工单选择项目即带出默认版本及对应模块分支。临时工单覆盖默认不写回，只有明确勾选后才保存。项目登记先于任务创建提交，任务失败不会撤销已经确认的项目资料；不会自动创建远程分支。

直接选择客户业务项目和主产品版本，然后自动展开其依赖，形成一张共享项目代码矩阵：

| 产品/版本 | 模块 | 版本基线 | 项目分支 | 当前策略 | 状态 |
| --- | --- | --- | --- | --- | --- |
| ECM V6 | core | 已配置基线 | 选择现有分支 | 使用已有项目分支 | 已验证 |
| Search 某依赖版本 | engine | 已配置基线 | 无 | 继承版本基线，修改时建项目分支 | 未定制 |

当前保存明确项目分支或留空继承基线。后续远程校验与授权建分支能力完善后，可扩展为以下三种策略：

- 使用已有项目分支：适合历史项目，选定后验证该仓库中的真实分支。
- 继承版本基线，修改时建项目分支：适合新项目或尚未定制的依赖模块。
- 待人工确认：已有定制但尚未查清，阻止执行，不冒充继承标准版本。

“未维护/不知道”与“确认没有项目分支”是两个状态。已存在的项目代码不能因系统没录入就被当成标准版本。

老项目提供“匹配现有 Git 资源”和“从 GitLab 导入分支”，展示候选而不是自动创建新分支；新项目可先继承产品清单，不立即创建任何远程分支。

默认只显示有项目覆盖的行，并显示“其余 N 个模块继承版本基线”；可切换完整矩阵检查。项目页和工单页可跳转到相同记录，避免维护两套分支。

客户项目换产品大版本时新增一组版本映射，不覆盖原版本的分支关系；历史工单继续指向原执行快照。

### 3.5 最少录入路径

一次性设置：在系统设置中选择一个工单规范 KB 总目录，后续产品、版本、模块和分支共用该入口。

首次手工录入：新建产品 -> 粘贴模块仓库 -> 新建版本并选择分支 -> 选择依赖版本 -> 登记已有 CI/镜像获取方式 -> 检查；规范目录由系统自动推导，无需逐版本选择。

后续新增版本：复制旧版 -> 修改变化模块的分支/仓库和依赖 -> 检查 -> 保存。

首次处理客户项目工单：选择或确认来源项目名称 -> 确认产品版本与已有分支 -> 转任务时登记项目 -> 后续工单选用项目自动带出，无需重复导入。后台可独立维护项目版本和分支。

## 4. 数据关系和唯一事实来源

下面是逻辑实体设计，字段名为建议，不是已经存在的表。

| 实体 | 核心内容 | 关系/约束 |
| --- | --- | --- |
| 现有 `product` | 名称、描述 | 保留 ID 和原有行为 |
| 现有 `product_version` | 产品、版本名、KB 目录、备注、启用 | 不改作代码配置或落盘目录 |
| 现有 `system_setting` 扩展 | 一个工单规范总目录 ID、目录显示名和配置修订号 | 复用现有 KB 连接；不为产品或版本另设根目录 |
| `code_repository` | 实例、仓库身份、规范 URL、备注 | 无凭据；同一实例项目不重复建档 |
| `product_module` | 产品、稳定模块标识、默认仓库/子路径、备注 | 模块标识在产品内唯一 |
| `product_version_module` | 版本、模块、该版本仓库、子路径、基线 ref 类型/值、已有 CI/产物获取方式和服务镜像映射 | 每版本每模块一条；显式保存，不执行时动态读默认仓库；仅登记，不改原 CI |
| `product_version_dependency` | 当前版本、依赖版本、纳入模块、备注 | 允许相互依赖，按版本 ID 去重展开；禁止有歧义的版本组合 |
| `customer_project` | 全局客户项目名称、默认产品与产品版本 | 与工作区执行项目分开；所有工作区复用 |
| `work_order_project_branch` | 客户项目、版本、模块标识、仓库 URL、实际分支 | 每客户项目每版本模块一条；不依赖工作区 Git 资源 |
| `work_order_source_mapping` | 工作区、MIS 连接、外部实体 ID、本地产品/版本/项目 ID | 名称只作候选，不自动当主键 |
| `work_order_context` | 来源工单、原文、整理稿、映射、关联主任务 | 工作区+连接+外部工单 ID 幂等 |
| `work_order_execution_plan` | 确认后的代码清单、配置修订号、批准范围 | 业务项目与工单执行项目分开 |
| `work_order_code_preparation` | 运行时、每仓库准确 SHA、路径、阶段和失败项 | 保留重试记录，关联计划，不覆盖旧运行证据 |
| `product_version_knowledge` | 产品/版本/模块、仓库身份、ref 类型/原值、授权范围、KB 目录/文档 ID、基线 SHA 和文档修订 | 按模块分支索引；客户差异与标准规范分开；同目录增量迭代 |
| `work_order_environment` | 本轮镜像清单、来源仓库/CI/SHA、镜像摘要、环境配置引用、运行与健康检查结果 | 与交付批次关联；主产品及依赖组成同一环境，不保存凭据 |

客户项目分支的唯一事实来源是全局 `work_order_project_branch`，保存对应版本模块的仓库 URL/ref，不创建工作区 `project_resource`。已有工作区项目的 Git 资源继续服务原有任务，不与共享客户项目分支双写或自动互相覆盖。

通过项目分支页面修改已有分支，会影响各工作区后续确认的工单；已冻结任务不变。预览时核对项目分支仓库与对应模块基线一致。待创建的分支名称只是计划，不作为“远程已存在”记录。

客户项目用自己的产品版本字段表示主产品，依赖版本由产品版本清单展开，不把所有依赖都塞进项目的单个 `product_version_id`。

全局目录数据和工作区数据分开：产品版本标准档案、客户项目及其分支可以复用；外部工单映射、工单、执行项目、小队、访问凭据和运行记录仍按工作区隔离。删除工作区不删除共享客户项目或分支。SQL 不引入外键或级联；由服务层验证和清理引用，所需索引按仓库规范单独迁移。

## 5. 分支如何选，项目分支如何建

### 5.1 先展开版本清单，再逐模块覆盖

1. 确认工单的主产品版本和客户业务项目。
2. 递归展开该版本的全部模块及声明依赖，依赖模块单独保留所属产品版本。
3. 按项目中对应版本模块的绑定覆盖，不只拿主产品项目分支套到其他产品。
4. 应用研发人员在本工单的明确覆盖。
5. 按仓库身份合并检出项，检查基线、目标分支和路径冲突，生成可确认的完整清单。

每个模块的读取基线优先级：

```text
本次工单已确认的覆盖
  > 客户项目对应版本模块的已存在分支
  > 产品版本模块的基线
```

没有项目分支时，只有“已确认继承”的模块才进入最后一项；待确认映射、应该存在但远程消失的项目分支直接阻塞，不静默回退。

MIS 的 `branch` 是原始来源信息，必须确认所属仓库后才能参与本次覆盖。依赖产品也有自己的版本和项目分支，不按 ECM 的版本号推测 Search 的版本。

### 5.2 读取基线、修改分支和交付目标分开

| 概念 | 作用 |
| --- | --- |
| 读取基线 | 这次应该看哪一套客户/产品代码；实际准备时解析为完整 SHA |
| 工单修复分支 | 从批准基线派生的隔离工作分支；沿用已有任务分支机制 |
| 项目/产品交付目标 | 修复最终提交到哪里；按项目策略与授权确定，不默认直接推版本主线 |

“从项目分支取代码”不等于在共享项目分支原地修改。跨机器成员都依据同一批准确 SHA 准备代码；提交和整合后生成新的成果清单，验证者使用整合后的准确 SHA。

分支/tag/commit 可以作为读取 ref；tag 或 commit 不能直接作为 push 目标，必须另选批准的分支。远程分支前进后不改变已准备的运行；下一轮是否更新基线要重新预览和确认。

### 5.3 老项目与新项目

**老项目**

先导入原有分支；明确匹配版本、模块、仓库再保存。发现预期项目分支不可访问时提示核对，不重建同名分支替代，不退到标准产品代码。

**新项目或尚未定制的模块**

先从版本基线统一准备全部相关代码。定位后明确需要修改哪些仓库；在首次写入对应仓库前申请目标分支，用户可在启动时授权“按命名规则为本次受影响模块创建项目分支”。

按授权为实际修改仓库从本次批准 SHA 创建项目目标分支，保存真实结果及共享项目分支映射，再开始修改。不修改的模块保持继承，不创建分支。单仓多模块只创建一条分支，同一次检出中的相关模块使用同一目标。

命名建议为 `project/<project-code>/<version-code>`，仅为可配置规则，不要求历史项目改名。名称冲突时核对已有分支及绑定，不覆盖现有远程分支。

远程创建和本地档案保存不是一个数据库事务：记录创建状态，若远程已创建但保存失败，恢复时核实同一分支与基线并补齐绑定，不重复建分支或误报成功。

产品本身、没有客户项目的缺陷使用产品认可的修复/MR 策略，不创建虚构客户项目分支。是否回补其他历史版本另行确认。

## 6. 工单界面如何消费这些配置

工作台新增“工单”。列表读取 MIS；详情完整保留原描述及来源状态，研发整理稿与原文分开。默认接口筛选中的“产品需求”只是来源过滤，不把“工单”限制成一种类型，实际类型查询能力需按接口验证。

工单详情的“代码范围”区不是只有一个分支输入框，而是后台配置解析后的结果：

| 产品/版本 | 模块 | 仓库 | 本次读取 ref | 来源 | 交付目标 |
| --- | --- | --- | --- | --- | --- |
| ECM V6 | core | 已配置 ECM 仓库 | 客户项目分支 | 项目覆盖 | 项目已有分支/MR |
| Search 依赖版本 | engine | 已配置 Search 仓库 | 该版本基线 | 标准版本 | 修改时按授权建项目分支 |

研发可以逐行改本次 ref，或选择“保存为该项目后续配置”；默认只影响当前工单，不改全局版本，也不自动覆盖项目配置。改仓库或依赖版本涉及代码范围变化，需要重新确认完整清单。

底部显示产品/模块数、按依赖版本去重后的实际检出数、依赖展开、知识准备状态、工单小队及运行条件。不同模块即使仓库地址相同也分别计数。启动入口前一次确认整个范围，而非要求用户逐仓库敲 clone。

- “保存草稿”：不 clone、不启动小队。
- “转为任务”：幂等创建工单主任务，暂不运行。
- “转为任务并启动”：确认计划后，先统一准备代码和知识，再放行修复阶段。
- 已转换工单打开原任务，继续修复不重复建单。

不强制用户先补全整个历史产品库；发现本单缺失的版本、模块、分支时集中补齐，保存后重新解析。

## 7. “一次把相关代码拉到一起”的执行设计

### 7.1 这是后台与运行时能力，不是给队长一串建议

服务端负责解析并冻结执行计划；接单运行时负责实际访问仓库、解析 SHA、统一检出和报告结果。不能让浏览器 clone，也不能服务端网络不通时假装所有运行时均无权限。

统一代码准备由持久化任务驱动，可查看进度、失败重试；只要一个必需仓库没准备好，整批就不能显示完成或让修复成员在缺代码的前提下继续。

准备顺序：

```text
已确认执行计划
  -> 检查运行时与凭据可用性
  -> 递归完整清单校验、目标目录冲突检查
  -> fetch 所有必需仓库，解析并记录准确 SHA
  -> 从固定 SHA 建立本次隔离 checkout/worktree
  -> 核对实际路径、HEAD、模块子路径
  -> 拉取适用规范，缺失则进入规范生成与回传
  -> 生成代码清单和环境说明
  -> 代码/知识均符合要求后进入定位修复
```

“一次拉齐”指用户一次操作触发整批准备，并非只有一个 Git 请求或一个 Git 仓库；之后修复、测试仍要各自进入正确的仓库/构建目录。

### 7.2 明确目录契约

多仓库产品与依赖：

```text
<work-order-root>/
  code/
    ecm/
      v6/
        main/                   # 默认主仓库
        backend/                # 额外模块，可自定义目录
    inbiz/
      v3/
        main/                   # ECM v6 声明依赖 Inbiz v3
  work-order-manifest.json       # 冻结计划和实际检出的 SHA
  work-order-compose.yaml        # 可选模板，不代表已部署
```

根目录绑定当前工作区、工单与运行。新计划使用 `code/产品英文标识/版本名称/模块落盘目录`；英文标识全局唯一，版本名称转换为安全的单段目录名。修改目录相关字段只影响新计划，不改变冻结的旧任务。所有路径位于已授权运行根内，不能把 KB 的 `directory` 当作本地根目录。

V9 单仓多模块：

```text
<work-order-root>/
  code/v9/v1/main/               # 一个主仓库模块即可
    <真实源码路径 A>/
    <真实源码路径 B>/
```

仓库内源码路径必须从实际仓库确认，不编造 V9 的目录名。同一仓库的多个源码目录通常只需一个主仓库配置，不必重复登记为模块。不使用符号链接伪装成多个仓库。

每个显式配置的模块拥有自己的检出目录；不同产品或模块引用同一仓库时仍独立检出，允许不同分支，不根据 URL 合并或偷偷挑一个分支。递归依赖按版本 ID 去重，允许环形关系，同一版本的各模块只检出一次；同一产品在一个计划里只能选择一个具体版本。

### 7.3 对现有 checkout 的具体扩展

现有 `multica repo checkout` 和仓库缓存可以处理单仓、认证和 task worktree，但目标目录目前主要按仓库短名生成；仅传 `ref` 并不能满足完整产品/模块布局。

需要补充：

1. 在现有缓存/checkout 链路中支持经验证的相对目标目录和准确基线 SHA；不能先 clone 再随意移动包含 Git 元数据的目录。
2. 批量准备协调器根据执行计划逐仓/受控并行调用，不另建绕过认证的 `git clone` 工具。
3. 确认路径归属、仓库身份与 HEAD，保留未提交工作；重试默认不使用 `--fresh`，不 reset 用户代码。
4. 为主任务和阶段子任务传递相同计划及成果清单，claim 不再只取执行项目的公共资源覆盖工单专属清单。
5. 处理远程创建分支、成员提交交接和交付登记，明确来源 SHA 与成果 SHA。

同一运行准备失败重试时复用已完成项，只重试失败项。新机器/新运行需要自己的隔离根目录，但依据同一准确 SHA 还原；不是让多台机器共用一个 Windows 路径。

### 7.4 进度与错误可见

逐仓状态：待检查、获取中、检出中、完成、失败。界面显示实际模块数、仓库数、路径和失败原因。

明确区分仓库无权限、运行时网络不通、分支不存在、模块路径不存在、目录冲突与磁盘不足。用户可以修配置后生成新计划，或对原计划重试，不把所有错误合并成“智能体不可用”。

## 8. 规范文档：一个总目录，自动归档并复用迭代

### 8.1 只配置一次总目录

系统设置的 KB 配置中增加一个工单规范总目录，保存真实 KB 目录 ID，建议配置键为 `work_order_knowledge_root_folder_id`。复用已有 KB 连接和授权，不新增每产品、每版本的根目录配置；未配置时集中提示补齐一次，而不是要求每个版本选目录。

系统在首次获授权的知识准备中自动建立以下层级；名称仅为结构示例，真实版本、模块和分支以档案为准：

```text
<工单规范总目录>/
  ECM/
    V6/
      <版本总览和依赖清单>
      core/
        <标准版本分支>/
          <模块规范文档>
        <客户项目分支>/
          <定制差异规范>
  Search/
    <依赖版本>/
      engine/
        <该模块实际分支>/
          <模块规范文档>
```

依赖产品的规范存放在其自己的产品/版本目录，主版本总览引用这些文档，不再复制一份到主产品下面。版本复制也只复制代码配置，不复制整套知识文档；新版本使用自己的目录，校验后可引用适用的已有内容。

### 8.2 目录与代码一一对应

目录层级固定为产品 -> 版本 -> 模块 -> 分支。服务端保存各层稳定实体 ID 与 KB 目录 ID 的映射，名称用于展示；改名不另建一套目录。建目录及重试按同一映射幂等处理，不仅凭同名文件夹猜测归属。

分支文件夹使用安全的单段名称和稳定身份后缀；`project/customer-a` 中的 `/` 不得被拆成额外目录。索引保留原始 ref，区分 branch/tag/commit，并纳入仓库身份；同名 ref、不同仓库或不同客户范围不能串用。客户分支后缀关联全局客户项目身份，仍位于同一总目录下；执行访问继续校验当前工作区的 KB 授权。

总目录不等于公开目录。标准规范和客户差异分别校验访问范围；客户内容只进入该客户分支下已授权的目录，不回写公共标准规范。若 KB 无法提供所需的子目录权限，则明确阻止客户内容上传，不通过另配第二个根目录或公开上传规避权限。

工单临时修复分支不逐单生成长期归档目录，规范归属已确认的产品版本分支或客户项目分支；临时成果记录在本次运行中。交付后确认目标分支的实际代码，再迭代该分支文档，不能把尚未交付的代码写成目标分支现状。明确选定的其他长期 ref 按自己的身份归档。

### 8.3 查找、复用和增量更新

每份模块分支规范记录产品/版本/模块、仓库及路径、ref 类型与原值、基线 SHA、KB 文档 ID、生成时间和修订记录。规范内容包括：

- 代码结构、产品/模块职责和依赖版本关系。
- 本地构建、运行和测试入口，必要环境和已知限制。
- 模块调用关系、关键数据流、修复注意事项。

准备时的顺序：

1. 根据已确认的完整代码清单，逐模块解析对应产品/版本/分支的规范索引及权限。
2. 已有规范且基线 SHA 一致：下载到当前运行目录，直接复用，不重新生成或上传。
3. 同一分支代码变化：对比上次规范对应 SHA 与本次 SHA，只更新受影响内容；无法可靠对比时重新校验该模块，不默认重建所有产品规范。
4. 无规范：按映射自动补齐缺少的目录，读取已准备代码并生成必要规范；校验后上传对应分支目录，保存实际目录/文档 ID 及基线。
5. 客户项目有定制差异：引用适用的标准规范，在同一总目录下对应客户分支的受限目录增补差异，不覆盖标准规范。

同一模块分支持续迭代原目录的文档及修订，不为每个 SHA、工单或运行新建目录；历史基线与文档修订关联保留，已运行快照继续引用当时的修订。目录内有同名文件不等于适用于当前基线。

默认将必须的规范准备作为修复前置步骤。KB 查询、建目录或上传失败如实显示受阻；人工可明确批准以本次本地规范继续，后续补传必须有记录，不能自动当作上传成功。修改总目录只影响后续确认的准备，旧文档和映射不自动搬移或删除，迁移需单独确认。

## 9. 首次 AI 梳理与后续发现

### 9.1 以原文仓库作为待识别种子

| 原文标签 | 仓库路径 | 入库前需确认 |
| --- | --- | --- |
| ECM | `edoc2v5/edoc2` | 产品和历史版本分支 |
| 搜索 | `edoc2v5/SearchEngine` | 独立产品还是模块、各 ECM 版本依赖关系 |
| InbizV6 | `InBiz/v6` | 是否与 V5 归为同产品的不同版本 |
| InbizV5 | `inbiz/InBiz`，位于另一实例 | 实例访问及历史版本映射 |
| V9 | `macrowing/opencontent` | 单仓模块实际路径和版本分支 |

实例信息从原文录入配置，不在本方案中附带访问凭据。这些是用户提供的起点，不代表本轮已经访问或验证仓库。

### 9.2 一次梳理流程

粘贴仓库地址 -> 选择对应 GitLab 连接 -> 仅读取已授权仓库信息/分支/tag/必要目录及版本文件 -> AI 生成候选 -> 人工预览确认 -> 批量写入档案。

候选分成产品模块、版本基线、依赖关系、项目分支四类。每条展示匹配依据、置信程度、冲突和将新增/更新的内容；无法判断的留待补齐，不能只凭分支名把客户归到某版本。

首次整理不创建远程分支、不 push、不默认 clone 全部历史分支；确需读取代码时在受控准备任务中执行。重复导入按仓库身份及显式映射匹配，不重复造产品和版本。

### 9.3 定时差异发现

只检查已授权、已纳入的实例/仓库范围；间隔由用户配置。发现新增仓库、分支/tag、已配置分支消失及基线变化，生成待确认清单。

已有分支正常前进只更新观测状态，不每次都要求重新确认项目归属；新映射、删除、跨版本变化等才要求审批。定时发现不会覆盖运行快照、删除历史版本或自动改变客户分支。

AI 批量梳理和定时发现可以后续增强，但不能用它们替代首期可手工维护完整档案的能力。

## 10. 专属小队、原有 CI 与镜像组合环境

### 10.1 小队与交付

工单小队以后单独创建并绑定，不使用现有开发小队。代码准备和产品配置能力不能依赖小队已创建：先能维护档案和预览；未绑定时阻止真正启动修复即可。

使用独立工单执行项目，客户业务项目只用于分支与业务上下文解析，避免继承客户原项目的开发流程。主任务、子任务都继承准确代码清单与验收条件。

队长在代码和知识准备好之后派修复任务；成员成果由整合角色汇总，独立验证针对最终 SHA。只对实际修改仓库提交和登记其原有 CI，不让每个只读依赖都跑一遍无关流水线。

历史版本各自的仓库和 CI 模式保持不动：不迁仓、不统一流水线模板、不改构建/发布脚本、不默认新增取消旧 CI 的规则。复用各仓库已有触发方式和流程；本平台只登记、查询结果、获取产物。已有流程需要人工操作时明确交接，不自动另触发一条 CI。

### 10.2 汇总各仓库镜像

每次交付记录实际修改仓库集合、各仓库最终 SHA/ref、验证结果及现有 CI。按该版本已登记的获取方式收集服务镜像，形成一份环境镜像清单：

| 内容 | 要求 |
| --- | --- |
| 产品、版本、模块与服务 | 保留归属；一个仓库可产出多个服务镜像 |
| 来源仓库、提交和 CI | 修改仓库关联本轮最终 SHA 及实际产出流水线 |
| 镜像地址与不可变摘要 | 保存实际 image digest，不仅依赖会被覆盖的 tag |
| 依赖镜像 | 未修改依赖复用该版本已确认可用的镜像，不为凑环境重跑全部 CI |
| 获取结果 | 区分构建失败、未产出镜像、镜像未推送、无拉取权限及版本不匹配 |

不要求旧 CI 为平台增加专用回调或新标签。已有构建元数据能够核对提交和镜像时直接读取；不能可靠对应时由人工核验并确认清单，不能把某个最新 tag 冒充本轮提交产物。没有镜像或旧 CI 不能运行时明确阻塞，交历史版本维护人按原流程处理，不在工单任务中擅自改造流水线。

### 10.3 把镜像组合成可运行环境

所有必要镜像就绪后，使用该版本原有部署清单或已确认的环境模板，将主产品、依赖产品及必需基础服务部署到同一个隔离测试环境。沿用项目实际使用的 Compose、Kubernetes 或其他部署方式，不强制历史版本迁移部署技术。

环境准备在 CI 之外编排：按镜像清单绑定各服务，配置网络、端口、启动顺序、健康检查、必要数据及版本匹配的初始化步骤。凭据引用授权环境的秘密配置，不写入镜像清单、规范文档或代码仓库。只有获授权的运行环境具备所需镜像架构、资源和访问权限时才启动，不覆盖已有客户环境或生产数据。

界面展示各仓库构建/镜像获取进度、整体环境状态、服务健康和可访问入口。任一必需镜像缺失或服务未就绪都不能宣称环境可用；失败保留诊断并支持针对性重试，不自动修改原 CI 来兜底。

多仓库交付、镜像齐备和组合环境可运行是首期闭环的必要条件。CI 通过不等于环境可用，环境可用也不等于业务验收；人工在该环境验收后才完成工单，也不在缺少 MIS 写接口时自动关闭外部工单。

## 11. 兼容、权限与实施边界

保留旧 `product`、`product_version` 的 ID、字段含义和已有 API；新增代码档案用独立实体/接口，不让老客户端保存版本基本信息时清空新配置。不存在代码档案的旧任务继续旧执行路径，工单新链路才要求档案完整。

已有版本的 `folder_id`、`directory` 继续服务旧功能，不改写为总目录或代码路径；新的工单规范只使用统一总目录和自动归档索引，不回退到各版本旧目录。历史知识若需纳入新目录，单独核对归属后导入，不默默搬移或删除。

旧项目 Git 资源不按名称自动转成版本模块映射，只提供确认导入。旧任务不重新解析或重拉代码；配置修改只影响后续确认的计划。

全局产品、版本及客户项目分支由系统管理员后台维护；处理人可通过本人已分派工单确认或登记客户项目，写回分支须明确选择。MIS 连接、工单、执行项目、小队绑定和启动权限按工作区校验；运行时只能准备当前授权任务中的仓库和目录。GitLab API 读写权限、运行时 Git 权限、MIS、KB 权限分别验证，凭据不进入浏览器持久存储、执行清单和生成文档。

接口按“保存档案 -> 解析预览 -> 确认计划 -> 启动准备 -> 查询结果 -> 授权分支创建 -> 记录成果”分离。保存、预览、导入候选不是启动执行的副作用。

最终提交和建分支要核实目标权限；不为本需求增加 GitLab 绕权、直接推保护分支或未经授权的发布路径。

## 12. 开发顺序与验收

### 12.1 必须交付的首期范围

1. 后台模块仓库、版本代码/依赖、已有 CI/镜像获取配置、单一 KB 总目录、项目分支矩阵及兼容迁移。
2. 解析器：依赖展开与版本去重、项目覆盖、工单覆盖、模块独立检出、路径/版本冲突和完整预览。
3. 工作台工单读取、完整描述整理、映射和幂等转任务。
4. 持久化统一代码准备，产品/模块布局、准确 SHA 和失败重试。
5. 总目录下按产品/版本/模块/分支自动建目录，规范复用、缺失生成和增量回传。
6. 老项目原分支使用、新项目受影响仓库按授权建分支并维护映射。
7. 专属工单小队执行、最终整合、独立验证、原有 CI 结果与镜像汇总、组合运行环境和人工验收，不改历史 CI。

可分批开发、逐步验证，但未完成第 4 项不能叫“一次拉齐代码”，未完成第 6 项不能叫“支持新老项目”，未完成真实交付不能叫“工单闭环”。

### 12.2 可后续增强

GitLab AI 批量梳理、定时差异发现、更丰富的历史对比和工单运营统计。外部 MIS 写回须等真实接口与授权明确。

### 12.3 试点验收场景

采用 ECM 某真实 V6 版本、一个真实依赖版本和两个客户项目：一个有历史分支，一个新项目。分支和版本名均以实际仓库为准，不用示例值冒充。

1. 后台维护 ECM 模块仓库、V6 模块基线、Search 依赖，只指定一次 KB 总目录；后续新增版本不再选目录，旧产品版本选择仍正常。
2. 老项目绑定其 ECM 原分支，Search 明确继承基线；工单自动带出，并可临时覆盖而不污染全局。
3. 一次启动，ECM 和 Search 代码实际都在一个根目录中，HEAD 与清单一致；一个仓库失败则整批不完成。
4. 首次准备自动建立产品/版本/模块/分支目录并上传规范；同模块分支和 SHA 的后续工单下载复用，代码变化只增量迭代原目录，不同分支不串用；建目录重试不重复，KB 失败不得误报成功。
5. 新项目先准备整套基线；只改 ECM 则只为 ECM 建项目分支，不为 Search 建分支。
6. 确需修改 Search 时，再按授权建对应项目分支并保存；之后同项目工单自动优先使用它。
7. V9 单仓产品只配置主仓库，内部源码目录随仓库一起检出；多个显式仓库模块则各自检出到独立目录，不重复登记交付。
8. 最终整合结果独立验证，各历史仓库按原有模式跑 CI；收齐修改仓库镜像并复用匹配的依赖镜像，组合环境健康后由人工验收。原 CI/构建脚本不变，不唤醒现有开发小队；缺镜像或服务不健康不能报成功。
9. 后台修改配置不改变已运行快照，重复导入/转单/准备重试不重复造数据或破坏工作目录。
