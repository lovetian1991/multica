# 工单首期试用指南

更新：2026-11-19。适用于先录入少量历史产品版本进行验收，不改造历史仓库或 CI。

## 入口与权限

- 工作台 -> 工单处理：普通成员只能查看和处理分派给自己的工单，权限由后端执行。
- 工作区所有者、管理员：可切换“全部工单”，导入、同步、维护配置及下派给工作区成员。
- 后台系统管理 -> 工单维护：部署管理员可选择工作区，使用独立维护列表；沿用 `MULTICA_SYSTEM_ADMIN_EMAILS` 白名单。
- 后台 -> 产品管理 -> 版本 -> 代码配置：维护每个历史版本的代码档案。
- 后台 -> 项目管理：全局维护客户项目的默认产品版本和模块项目分支，所有工作区共用，不需要选择工作区。
- 后台 -> 系统设置 -> 统一规范根目录：只配置一个 KB 总目录。

Web 和桌面共用工单页面。未手动选择语言时默认简体中文；已选英文的账号可在“设置 -> 偏好设置 -> 语言”改为“简体中文”，选择会同步到账户。

## 配置一个老版本

1. 在产品管理维护产品名称和全局唯一的英文标识，如 `ecm`、`inbiz`，再创建或选择历史版本进入“代码配置”。已有产品需手动补齐英文标识，不会用难以辨认的产品 ID 代替。
2. 未配置版本默认有一个“主仓库”模块，标识 `main`；只填仓库 URL 和明确分支/tag/SHA 即可，单仓版本不用再添加模块。有其他仓库再添加模块，可填写名称和备注。模块标识使用字母、数字、下划线、连字符。
3. “代码落盘目录”留空使用模块标识，可改为 `backend` 或 `services/api`，运行时自动新建。各模块目录不能重复或互相嵌套。“仓库内子目录”折叠在高级项中，仅指仓库里已经存在的路径，不用于新建目录。
4. 如果依赖其他产品，在“依赖产品与版本”点击“添加依赖”，选择依赖产品和具体版本，例如 ECM v6 依赖 Inbiz v3；缺少产品或版本可直接在此新建。选中的依赖可修改版本、打开其代码配置或移除。可以先保存依赖关系，再补齐双方仓库；实际校验代码计划、转任务前必须完成所有版本的模块配置。保存时拦截循环、重复和同产品多个版本冲突，计划递归纳入全部依赖模块。同一仓库可在独立模块目录使用不同分支。
5. 默认“模块代码”页只维护仓库和基线。服务镜像、CI 和 Compose 放在“构建与部署（可选）”，不要求先填这些才能维护代码。
6. 需要时在可选页登记各仓库现有的 CI 地址、服务名与镜像引用，以及主版本的“环境 Compose”。一个模块可以登记多个镜像；不要改原流水线、构建入口或镜像命名。使用确定的镜像 tag 或 digest，不填写密钥。切换页签再保存不会清空其他页已有配置。
7. 在系统设置选择规范总目录。新计划使用 `产品英文标识/版本名称/模块标识/转义后的分支` 命名。版本名称中的路径分隔符等非法字符替换为 `-`。

每个版本单独保存仓库、分支和依赖，修改新版本不覆盖老版本档案。版本的原有知识库字段不改作工单规范目录。

## 配置执行与客户分支

1. 在工作区新建独立的“工单处理”执行项目，不添加 Git、本地目录或其他项目资源。保留搁置状态，不绑定现有开发小队的自动处理人。
2. 在“工单设置”选择该专用执行项目。工单小队可以暂不设置，之后单独创建再绑定，不会回退到现有开发小队。
3. 客户项目可在“后台 -> 项目管理”直接新增、修改名称和删除，不必先有工单。新增时先填名称，再选择产品版本并保存模块分支；同名项目会提示复用。首次工单转任务时也可确认项目名称、产品版本并登记到同一份档案；已有项目按选择或唯一同名来源项目复用。同名项目不唯一时须明确选择。
4. 在“后台 -> 项目管理”直接选择客户项目，维护默认产品版本。右侧“维护模块仓库”和“维护产品依赖”可新增、修改、移除所选版本的模块及依赖，这些修改影响所有使用该版本的项目；未配置仓库时显示待配置提示。配置完整后页面一次展开主版本和全部递归依赖，为有定制的模块填写实际已有分支；留空则继承版本基线，也可用行末按钮移除项目分支、恢复基线后保存。分支保存到共享客户项目，不需要创建工作区 Git 资源。客户项目的版本升级不会覆盖其他历史版本的分支映射。
5. 没有绑定的模块使用版本基线；如果老项目实际已有定制，请先查清并绑定，不要把“没录入”当作“没有定制”。
6. 删除项目需确认，会同时删除该项目所有版本的分支配置，但不删除产品、版本、工作区执行项目或任务。被任何工单引用时拒绝删除并保留配置；未转任务的工单可先解除项目关联，已转任务的工单保留历史关联。

分支优先级为：工单明确覆盖 > 客户项目绑定 > 版本基线。配置中的仓库和版本基线保持不变；探针在工作区 GitLab 账号的个人 fork 中准备项目分支，不在标准产品主仓库创建项目分支。

“工单设置”只保留本工作区的执行项目、专属小队和 MIS 接入。后台项目管理为系统管理员入口；普通处理人可读取共享档案，通过本人已分派工单确认项目，不获得后台维护权限。共享仓库 URL/分支不包含令牌，不代表其他工作区自动获得仓库访问权限。

产品、版本、模块、依赖、客户项目及项目分支全局复用；工单、执行项目、负责人、小队、MIS 和运行权限仍按工作区隔离。删除某个工作区不会删除共享档案。

迁移 `626_global_customer_projects` 保留原客户项目 ID 和版本模块分支，将已登记客户项目迁到独立全局档案，原工作区项目和任务保持不动。新建的全局客户项目不能直接表示为旧版工作区项目；若需回滚且存在这类记录，迁移会拒绝回滚，需先导出并明确映射，不能直接删表丢数据。

## 工单试用

1. 管理员先“导入工单”，填原始编号、标题、描述、版本和负责人，无需先接通 MIS。
2. 用普通成员登录“工单处理”：只能看到自己的单，修改处理草稿、客户项目和处理阶段，保存后刷新确认保留。
3. 确认版本后点击“校验代码计划”，检查主产品和全部依赖模块、仓库、分支、目录及备注。需要临时覆盖分支时填写后再次校验。
4. 点击“创建处理任务”，先确认项目、产品版本和实际模块分支。来源项目名称会预填；唯一同名项目复用并预览其项目分支。选已有客户项目时自动带出该项目维护的默认版本，仍可在转任务前调整。
5. 本单临时分支默认只作用于本单；勾选“将本单指定分支保存为项目分支”才登记为各工作区共用的项目长期配置。不勾选不会清空已有项目分支，也不会改变已有项目的默认版本。
6. 点击“确认并创建任务”，登记/更新客户项目后关联一个原生搁置任务并冻结计划，重复转任务不重复创建。若登记后配置发生变化，需对刷新后的计划再次确认。如果创建任务失败，已经登记的项目会保留，可修正执行配置后重试，不必重新导入。
7. 点击“打开任务”确认上下文。创建任务不会自动运行；配置好专属小队或明确分派后，再按原任务流程人工启动。

转任务后不能再修改代码版本、客户项目或分支快照；原工单负责人、草稿和处理阶段仍可维护，但不会改写已经创建任务的说明和执行计划。

## 连接 MIS

在“工单设置”填环境根地址和凭据 JSON。凭据格式为 `{"headers":{"appid":"...","siteoutid":"..."},"token":"..."}`，按实际接口要求填写允许的业务认证头，不把凭据放进仓库 URL、备注或 Compose。服务端需要既有系统设置加密密钥，界面只返回是否已配置，不返回明文。

“同步 MIS”仅调用文档提供的 `/QcWorkOrder/List` 查询，排除草稿，每次最多 100 条；有下一页时按钮显示后续页码，再次点击继续。本版不做定时同步，不自动猜测内部负责人、产品版本或客户项目映射。同步只更新原单内容，保留本地草稿、负责人、阶段和任务关联，不写回或关闭 MIS。

## 运行时与环境边界

必须使用包含本次工单能力的新版运行时，并在当前工作区设置中连接 GitLab。探针使用当前工作区配置的身份，不要求连接人等于当前操作人；共享工作区同样使用该配置，不自动切换到成员自己的账号。令牌由服务端加密存储，仅供已授权探针解析，不能写入仓库 URL 或智能体环境。

探针核验个人仓库确实是配置主仓库的 fork；不存在时在该账号下创建，同名但非对应 fork、导入失败或权限不足会明确报错。项目分支默认 `proj-项目名称全拼音-产品版本`；已保存的项目/工单分支覆盖仍优先。主仓库版本基线只读，个人项目分支同步禁止强推，冲突时保留代码并停止。

智能体在已准备的模块功能分支上开发并提交；任务成功后由探针推送个人功能分支，并向主仓库配置的产品版本分支发起跨仓库 MR。探针不自动批准或合并。审核链接写入完成评论和运行清单，重复提交复用同一 MR。未提交文件、推送或 MR 失败会使交付失败并保留本地代码；只有确认本地提交已进入主仓库目标分支后才允许清理。提交 MR 时请求合并后删除该功能分支，不删除个人项目分支。

新版运行时会先准备计划内全部仓库，再启动智能体。新计划的目录为 `code/产品英文标识/版本名称/模块落盘目录`。例如：

```text
code/
  ecm/v6/main/          # 主仓库，没有其他模块也使用此目录
  ecm/v6/backend/       # 可选的其他模块
  inbiz/v3/main/        # 声明依赖的具体产品版本
```

每个模块独立检出，重复到达同一依赖版本只展开一次。单仓产品只维护一个主仓库，无需为仓库里的每个源码文件夹重复加模块。旧任务沿用冻结的原目录；修改英文标识、版本名称或模块目录只影响新生成的计划。拉取失败、分支或仓库内子目录不存在时停止准备，不在缺少依赖的情况下继续启动。

运行目录产出 `work-order-manifest.json`，包含计划与实际检出的 SHA；填写了 Compose 时额外写出 `work-order-compose.yaml`。这些是准备结果，不代表 CI 已通过或环境已经部署。

当前尚未自动收集 CI 产出、替换 Compose 镜像或启动组合环境，需要操作人员获取各仓库实际镜像后手动部署并验收。KB 当前只有总目录与规范路径规则，尚未自动建目录、下载、生成或回传规范。专属工单小队也尚未自动创建。

## 验证代码准备

先为目标后台单独登录一个 CLI profile，配置该后台的 `server_url`、工作区 `workspace_id` 和本机 `workspaces_root`，再启动同一 profile 的探针。不要复用连接其他环境的默认 profile。

```powershell
multica --profile local-code-check daemon start --no-auto-update --no-auto-reload
multica --profile local-code-check repo prepare-product <产品版本 UUID> --project-name "客户项目名称"
```

命令读取探针连接后台的当前产品配置，递归展开依赖，并调用处理任务时的同一套共享仓库准备逻辑。循环依赖只展开一次，仓库权限、分支或子目录错误会明确失败，不回退到默认分支。

默认核验或创建个人 fork，并将配置版本同步到个人项目分支，实际验证个人 fork 的写入权限。`--personal-fork=false` 只验证配置基线读取，不创建个人分支。子模块缺少来源映射、未初始化或检出版本不匹配时拒绝将模块标记为准备完成；不会猜测来源仓库。

输出为逐行 JSON：`plan` 包含实际后台地址、完整清单和落盘根目录；`preparing` 表示开始准备模块；`resolving_fork`、`checkout`、`synchronizing_project_branch` 区分 fork 核验、检出和项目分支同步；`ready` 包含同步后的实际 SHA；收到 `complete` 才代表全部完成。首次克隆或为旧 fork 补齐大型版本对象可能较久。任一模块失败或连接中断时，命令以非零状态退出，不能视为完整准备成功。

每次验证默认使用 `workspaces_root/.code-checks/<工作区 UUID>/product-*` 下的独立目录，并生成 `work-order-manifest.json`；`--workdir <已有验证目录>` 可复用当前工作区已有目录，保留已核验的 fork 回执和本地开发提交。Git 对象复用同一工作区的上游仓库缓存，模块各自隔离 Git 元数据。本命令会同步个人项目分支，但不启动智能体、不推送功能开发、不创建审核 MR、不主动调用 CI 或部署。GitLab 自身可能按个人 fork 的 push 规则触发流水线，准备前须确认 fork 的 CI 配置。

## 已执行验证

- 实库接口测试：个人权限、重复导入保护本地字段、过期编辑冲突、幂等转任务、计划冻结及子任务继承、产品版本归属与代码配置清理，以及项目登记、同名复用、版本分支历史保留和清空覆盖后回退基线；产品英文标识的唯一性、旧客户端省略字段保留原值，以及保存前的循环/重复依赖和版本冲突校验。
- 代码解析与运行时测试：依赖和分支校验、仓库 URL、MIS 只读分页、共用仓库检出、冷缓存准备，以及使用本地 Git 仓库实际检出主产品和依赖版本、核对目录与准确 SHA。覆盖相同仓库不同分支的独立模块及不安全/嵌套目录拦截。
- 浏览器：默认主仓库只填仓库和分支即可保存、追加模块、自定义落盘目录、按产品选择具体依赖版本并校验完整计划；管理员下派、成员只查自己的单、草稿保存重载、后台独立维护入口、确认后登记项目、后续选择项目自动带出版本与分支、来源同名复用不重复创建、切换代码配置页不清空部署信息，以及桌面/手机布局。中文作为实际验收界面。
- 共享 API 与语言选择测试、Web/Core 类型检查、工单页面局部 ESLint。
- 全局共享回归：两个工作区复用客户项目、默认版本和模块分支；实际删除来源工作区后，共享档案及分支仍可使用，原执行项目不向其他工作区开放；普通成员和工作区管理员不能维护全局后台档案。
- 后台项目维护回归：独立新增、名称与同名校验、改名后保留版本及分支、工单复用后台档案、删除确认与取消、引用保护和删除后清理项目分支；包含桌面与手机浏览器布局。
- 依赖维护回归：只有当前产品时仍有添加和新建入口，就地新建产品及版本、仓库未配置时保存依赖、重开并移除依赖；仓库缺失仍阻止执行计划，补齐后展开主产品与依赖目录。项目右侧可从空配置补齐主仓库、添加/移除模块并清除项目分支覆盖。
- 迁移回归：隔离测试中验证旧客户项目 ID、分支和执行项目保留，验证可回滚数据的往返迁移，并确认存在无法映射的全局客户项目时拒绝回滚、不丢数据。

没有运行真实智能体、业务仓库 CI 或实际部署组合环境。仓库其他范围已有类型测试和数据库清理清单问题，不据此宣称全仓测试通过。
