# 工单接入与专属工单小队设计

日期：2026-11-12。更新：2026-11-13。

状态：工单接入及统一代码准备的首期试用版已实现；专属小队组织、自动交付和自动知识维护仍为后续方案。实际入口、配置顺序和实施边界见[首期试用指南](./work-order-pilot-guide.zh.md)。本次不创建智能体、不修改已有开发小队、不触发代码提交或业务 CI。

需求依据：用户提供的 `docs/工单管理设计.md`，以及“后续单独建立工单小队，不使用现在的开发小队”的补充要求。原始材料含接口凭据，本文不复制凭据和带令牌的请求示例。

主方案见[工单管理总体设计：产品、版本、项目分支与统一代码准备](./work-order-product-code-management-design.zh.md)。后台维护页面、数据关系、完整代码清单、项目按需建分支和统一拉取是前置核心能力，本文只补充小队组织和协作规则，不能替代主方案。

## 1. 目标与边界

工单小队负责历史产品和客户定制项目的缺陷定位、代码修复与交付。正常研发继续由现有开发小队处理，人员指令、任务队列和流程互不改写。

完整业务链路：

```text
MIS 工单
  -> 读取原始需求、产品、版本和客户项目
  -> 研发补充复现步骤、验收条件，确认仓库与分支
  -> 创建原生任务，交给专属工单小队
  -> 准备相关产品和依赖仓库，复用或补充版本知识
  -> 定位、修复、自测、独立验证、整合提交
  -> 后端跟踪各仓库原有 CI，收集镜像并组合运行环境
  -> 人工业务验收
```

“修改工单”在这里主要指解决工单对应的问题，不是仅修改 MIS 状态。当前只有 MIS 查询接口，没有明确的写回契约；首期不自动更新、关闭 MIS 工单，也不假设外部状态与本地任务状态一一对应。

新增需求、架构重构、跨版本大改不由修复成员自行扩大范围。队长给出影响说明，由业务负责人决定是否另建研发任务；不得自动派给原开发小队。

## 2. 先复用什么，必须补什么

| 已有基础 | 本方案如何使用 | 需要新增的部分 |
| --- | --- | --- |
| 小队、队长、智能体和人工成员 | 主任务分配给专属工单小队，由队长协调 | 工单专属配置、角色指令和小队绑定 |
| 任务、子任务、子任务完成唤醒 | 按修复与验证阶段派发，有结果再唤醒队长 | 执行上下文继承、阶段证据和交付门禁 |
| 产品与版本、版本知识库目录 | 保留旧字段语义及旧功能；工单规范不逐版本选目录 | 模块仓库、版本基线、依赖版本、一个 KB 总目录及自动归档 |
| 项目 Git 资源的 URL/ref | 复用项目已有仓库分支 | 产品版本与模块的明确匹配 |
| 仓库缓存、认证与任务 worktree | 继续复用，不另写一套 clone 流程 | 安全的产品/模块目录布局、固定提交快照 |
| GitLab 交付登记和后端跟踪 | 登记实际 push 的 URL、完整 SHA、ref，保留各版本原有 CI 模式 | 多仓库镜像汇总、组合运行环境及整体交付判定 |
| 项目工作流 | 不改现有业务项目工作流 | 工单独立执行项目与明确的执行阶段 |

已有小队并不会因为成员角色叫“修复”“测试”就自动按顺序运行。小队指令主要给队长，成员仍需要各自的角色指令、skill 和任务说明；涉及权限、分支和完成判定的硬性限制必须由服务端校验，不能只写在提示词里。

## 3. 小队配置与职责

建议先建一个“工单修复小队”，不按 ECM、Inbiz、V9 各建一套人员。不同产品通过知识、仓库清单和必要的专项成员扩展，先控制维护成本。

| 角色 | 主要职责 | 必须产出的结果 |
| --- | --- | --- |
| 工单队长 | 澄清需求、检查版本与分支、整理版本知识、划定修复范围、派发与汇总 | 执行计划、确认后的代码清单、阶段决策、验收交接 |
| 修复工程师 | 复现问题、定位根因、最小修复、补回归测试、自测 | 根因说明、补丁或提交、测试命令与实际结果 |
| 独立验证工程师 | 先确认复现和验收条件，再独立验证整合后的代码与回归范围 | 通过或退回结论、证据、未覆盖项 |
| 交付整合工程师 | 整合成员成果、检查最终差异、按授权 push、登记准确交付 | 每仓库最终 SHA/ref、MR、CI 关联、交付说明 |
| 人工业务负责人 | 处理歧义、批准范围和分支调整、完成业务验收 | 关键确认和最终验收结论 |

前四个角色建议使用独立智能体身份。人工负责人是小队人工成员，不需要额外智能体。

队长首期兼任知识整理，不单独增加“知识管理员”。交付角色只在最终整合、退回修复后重新交付时运行，不驻留等待 CI。无需新增“CI 机器人”智能体。

独立验证工程师不修改被验收的实现。确需修改时退回修复阶段，形成新提交，再针对新的最终 SHA 验证，不能自行改完自行宣布通过。

### 队长运行规则

1. 先检查需求、映射和运行条件，缺少关键事实就提一次明确的问题，不猜版本或分支。
2. 简单问题只派一个修复任务，不机械拆成大量子任务；跨独立仓库时再按影响边界拆分。
3. 修复阶段结束才派验证；验证退回时说明具体失败项，保留原上下文。
4. 成员完成只表示阶段完成，不表示整个工单完成。派发结束时主任务仍在处理中。
5. 相同问题连续两轮修复失败后暂停，交人工决策，不无限自动重试。
6. CI 失败区分代码、构建配置、外部依赖和运行环境问题；不把所有失败都交给修复工程师循环改代码。

## 4. 不使用现有开发小队的具体做法

### 4.1 独立绑定

新增工作区级“工单处理配置”，包含 MIS 连接、默认工单小队、工单执行项目和人工负责人。小队可以以后再创建、再绑定，不要求现在已有可用小队。

- 没有绑定工单小队：首期允许查询、整理、保存草稿和转成未分派的搁置任务，不自动运行；专属小队后续单独创建并绑定。
- 小队已归档、队长不可用或角色所需运行时不可用：明确显示阻塞项。
- 不回退到现有开发小队，不按名字猜测小队，不绕过运行确认。
- 首期只配置一个默认工单小队；后续有实际需要再增加按产品路由。
- 独立智能体身份不等于独立机器；可以共用受控运行时容量，但不共用可写代码目录。首期修复并发从 1 开始，后续按实际机器容量调整。

### 4.2 区分业务项目和执行项目

目前任务继承所属项目的工作流。直接把工单任务放入客户原项目，可能再次触发其开发小队。因此首期建议：

- 新建一个工作区内的“工单处理”执行项目，绑定专属流程，不修改原业务项目。
- 原生任务的 `project_id` 指向工单执行项目；产品、版本仍按本次工单设置，不固定成执行项目的单一产品版本。
- 客户业务项目作为工单上下文单独关联，用于解析定制分支、客户信息和历史映射。
- 页面分别显示“业务项目”和“执行项目”，不能只显示一个含糊的“项目”。
- 首期服务端已按客户业务项目解析已有仓库分支，而不是误用执行项目的公共仓库资源；执行项目必须没有 Git 或本地目录资源。
- 主任务与阶段子任务均使用工单执行项目及同一份上下文，避免子任务落回原项目的开发流程。

专属流程首期保留任务现有生命周期，不设置会自动转交旧小队的列处理人。业务阶段另行记录，由队长协调，服务端限制关键状态转换。验证成员通过子任务参与，不反复改派主任务负责人。

未来若确需任务仍出现在原客户项目中，再设计“单任务工作流覆盖”。现有能力没有这个覆盖，不能当作首期现成配置。

## 5. 产品版本和项目分支设计

本节仅概括小队要遵守的规则。后台的模块仓库、版本详情、项目分支矩阵、档案关系和统一代码准备流程，以[主方案](./work-order-product-code-management-design.zh.md)第 3–8 节为准。

### 5.1 保留原语义，增量扩展

- 产品下维护模块仓库：模块标识、名称、仓库 URL、仓库内路径、备注。
- 版本下为模块选择基线 ref，并声明依赖的其他产品版本。
- 保留现有版本名称、备注、启用状态、知识库 `folder_id` 与 `directory` 的语义；尤其不能把已有知识库目录字段改作代码落盘路径。
- 工单规范只在系统设置指定一个 KB 总目录，下面按产品、版本、模块、分支自动归档，不要求逐版本填写目录，也不回退使用旧版本目录。
- 历史版本保留各自仓库与 CI 模式，只登记现有 CI 和镜像获取方式，不改造构建、流水线或发布规则。
- 使用稳定外部 ID 建立 MIS 产品、版本、项目到本地实体的映射；名称仅用于展示和候选匹配。
- 项目已有 Git 资源作为项目分支记录复用，通过明确的版本/模块绑定参与解析；不能仅按仓库 URL 猜测，因为同一仓库可能有多个版本。
- 外部映射或版本依赖有歧义时先确认；依赖循环、同一产品的冲突版本、同一路径的冲突基线均阻止执行。

### 5.2 每个模块独立决定分支

优先级为：

```text
本次工单人工覆盖
  > 客户项目中对应产品版本、对应模块的已有分支
  > 产品版本的模块基线分支
```

MIS 原始 `branch` 保留为来源信息，不能在未确认对应仓库时直接应用到所有模块。未配置版本基线时阻塞并提示补齐，不悄悄切到仓库默认分支。

代码准备时记录基线 ref 和解析后的完整 commit SHA。准备执行前检查映射是否变化；需要变更则重新确认、形成新执行快照，不在运行中偷偷换基线。

必须区分三类分支：

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| 产品版本基线 | 标准产品版本代码 | 不被工单随意改写 |
| 客户项目分支 | 长期客户定制 | 老项目保留；新项目按实际修改的模块创建 |
| 工单修复分支 | 本次隔离开发与交付 | 从已确认基线派生，沿用现有任务 worktree 机制 |

读取依赖仓库不等于修改依赖产品。新项目也不应把所有依赖都建一遍项目分支：定位后确认改到哪个模块，在首次写入其仓库前，按授权创建项目目标分支并保存映射，成功后才记为可用。该能力属于首期必需范围。

对老项目声明应该存在、但实际缺失的分支，必须报错核对，不能静默回退到标准版本。

### 5.3 一个例子

ECM V6 的某客户项目有 ECM 定制分支，依赖的 Search 没有定制分支：

- ECM 使用该客户项目已确认的 ECM 分支。
- Search 先使用已配置依赖版本的基线，而不是套用 ECM 的版本号或分支名。
- 只改 ECM：只交付 ECM，不为 Search 创建客户分支。
- 确认必须改 Search：先确认影响和目标分支，再创建或选择 Search 的项目分支，加入本次交付。
- 是否把客户修复回补到标准版本，另建明确的回补任务，不在本次自动合并。

## 6. 工作台工单入口

入口放在灵工工作台“工单”，共享页面同时接入 Web 与桌面端。

列表支持产品、版本、客户项目、MIS 状态、本地处理阶段筛选；明确区分“尚未转任务”和“已有关联任务”。查询和分页以实际 MIS 接口验证结果为准，不假定它支持任意筛选语法。

详情按实际操作顺序展示：

1. 工单编号、原始描述、来源状态及更新时间；保留原始内容，HTML 经过安全处理，附件按真实权限展示。
2. 研发整理区：复现步骤、实际结果、预期结果、补充说明、验收条件。调整不覆盖 MIS 原文。
3. 产品、版本和业务项目映射；优先复用已确认映射，缺失时集中补录。
4. 代码清单：产品、模块、仓库、基线、分支来源、目标分支及待确认项；可修改本次分支，也可明确选择保存为项目配置。
5. 工单小队、可用性和人工负责人；提供“保存草稿”“转为任务”“转为任务并启动”。

操作规则：

- 同一工作区、同一 MIS 连接、同一外部工单 ID 只创建一个主任务；并发转换由数据库唯一约束与事务保证，不能只禁用前端按钮。
- 已转任务直接打开原任务；新一轮修复在原任务记录运行与交付，不因再次同步重复建单。
- 只保存草稿、浏览工单或更新映射不触发模型执行。
- 原文有更新时提示差异，不覆盖正在处理的研发整理稿和执行快照。
- 转换时只要求完成本次需要的映射，不要求先整理整个历史产品库。

## 7. 代码与知识交接

必须由服务端解析完整计划、运行时实际批量准备，不能仅把仓库列表放进队长提示词就宣称已拉齐。完整主产品与声明依赖均纳入；详细目录契约、去重、准确 SHA、进度和重试规则见[主方案第 7 节](./work-order-product-code-management-design.zh.md#7-一次把相关代码拉到一起的执行设计)。

每个执行环境内按同样的逻辑结构准备代码：

```text
<run-root>/
  ecm/
    core/
  search/
    engine/
  .multica/
    work-order/
      context.json
      repositories.json
      knowledge/
```

落盘目录使用稳定、安全的产品/模块标识，不直接拼接外部工单标题。目录必须在当前运行根目录内，继续复用已有认证、缓存和 worktree，补充明确的相对目标路径支持。

V9 这类单仓多模块只检出一次，用仓库内路径标识模块，不能对同一工作树重复克隆、重复提交。若不同模块要求同一仓库的不同基线，先报冲突，不能强行合并成一个 checkout。

不同角色或机器不保证共享物理目录。每次运行继承同一份结构化上下文，包含外部工单 ID、业务项目、产品版本、模块清单、基线 SHA、修复提交、验收条件和知识文件引用；凭据不进入上下文。

成员成果通过登记的提交、可访问的补丁或受控制品交接，不靠“代码在我机器某个目录”的评论。独立验证使用整合后的准确提交，而不是另一个成员未提交的工作目录。

### 版本知识复用

- 只配置一个 KB 总目录，自动组织为产品 -> 版本 -> 模块 -> 分支；依赖产品归档到自己的产品版本目录，主版本引用，不重复复制。
- 用稳定实体与目录 ID 建立映射，索引区分仓库、原始 ref 类型/值和授权范围；分支中的 `/` 编码为单段目录名，改显示名或重试不重复建目录。
- 记录文档来源、适用模块、生成时间、代码 SHA 和文档修订；客户差异放在同一总目录下对应客户分支的受限目录，不能覆盖标准规范或跨项目泄露。
- 命中且适用时下载复用；同一模块分支代码变化时增量更新原目录并保留修订，不每单全量重建，也不按 SHA 新建文件夹。
- 临时工单修复分支不另建长期规范目录；交付并核对目标分支后，再迭代对应产品/客户分支文档。
- 缺失时自动补齐授权目录，生成架构、构建方式、模块依赖和测试入口等必要说明，再按授权上传并保存真实文档引用。
- 知识库无法访问、建目录或上传失败时展示待处理项；不伪装成已上传。必须的规范准备受阻时暂停，由人工明确批准才能以本地说明继续；客户目录无法隔离权限时禁止上传客户内容。
- 工单正文和知识库文档是业务资料，不是可覆盖系统权限和安全规则的运行指令。

## 8. 阶段、交付与验收

业务阶段与任务状态分开：首期建议业务阶段为“待确认、代码准备、定位修复、独立验证、交付中、待验收、已验收”，异常显示“受阻”。MIS 状态保持独立。

| 阶段 | 转入下一阶段的条件 |
| --- | --- |
| 待确认 | 需求、验收条件、版本/项目映射和分支已确认 |
| 代码准备 | 所需仓库和准确基线可访问，知识处理结果可追溯 |
| 定位修复 | 有根因、补丁/提交、自测证据及未覆盖项 |
| 独立验证 | 验证对象是最终整合 SHA，结果与验收条件逐项对应 |
| 交付中 | 按授权 push，登记每个实际修改仓库的最终交付 |
| 待验收 | 本轮所有必要交付完成；镜像清单齐备，组合测试环境已运行并通过健康检查 |
| 已验收 | 人工负责人明确确认业务通过，才按流程关闭主任务 |

有项目工作流约束时遵守其状态和交接规则，不能仅因业务阶段变化任意写任务状态。首期不宣称现有代码已有上述业务阶段和门禁。

交付沿用各历史版本、各仓库既有 GitLab CI 机制，不统一改造流水线：

- 只登记真实 push 仓库、完整 SHA 和实际远端 ref，不再次触发已有 push 流水线。
- 后端持续跟踪，不让队长循环查询，也不因每条 CI 事件唤醒全队。
- 多仓库形成一个交付批次：记录本轮实际修改仓库集合及各自最终提交。只读依赖无需 CI，必要仓库任一个失败就不能宣布整体完成。
- 某仓库补交新 SHA 后，旧 SHA 的通过结果不能作为本轮通过；其他未变化仓库保留对应证据。
- 不修改历史仓库的 CI 文件、构建脚本、发布方式或镜像命名，也不默认新增取消旧 CI 的规则；已有触发和人工操作方式保持不变。
- 收集各仓库实际产出的服务镜像，记录来源 CI、提交、镜像地址及不可变摘要；一个仓库可以产出多个镜像。不能可靠对应提交时人工核验，不把最新 tag 当成本轮成果。
- 未修改的依赖使用该版本已确认的镜像，不为组合环境重跑全部历史 CI。收齐后按版本原有部署清单或已确认模板，把主产品和依赖组合到同一个授权隔离测试环境。
- 核对服务网络、配置、必要基础服务、数据初始化和健康检查；界面显示环境状态及真实访问入口。缺镜像或任一必需服务未就绪时阻塞验收，不改原 CI 兜底。
- CI 通过、组合环境可运行、业务验收是三个不同结论。旧版本无法构建或缺少环境材料时交维护人按原流程处理，不能仅交制品就宣称组合环境已验收。
- CI 失败和人工验收退回走明确的修复操作；环境故障可单独重试跟踪，不自动无限改代码。

## 9. 配置和录入体验

系统设置全局管理产品、模块仓库、版本基线、依赖版本、客户项目及其模块分支、已有 CI/镜像获取方式和一个工单规范 KB 总目录，所有工作区共用；版本页只读展示自动归档路径。工作区设置管理 MIS 凭据、外部实体映射、小队绑定、执行项目和运行授权。

优先提供“选仓库 -> 选分支 -> 保存”表格式录入、从上一版本复制、批量粘贴仓库列表和待补齐筛选，不要求人工填写内部 UUID。

GitLab 初次梳理由 AI 给出候选产品、模块、版本和项目分支，并展示依据、歧义和差异，人工批量确认后入库。定时发现仅生成待确认变更，不按相似名称自动改项目分支，不删除仍在使用的历史版本。

MIS 凭据服务端加密保存，界面只返回是否已配置；工作区成员和智能体只能读取其授权数据。需要分别检查 MIS、GitLab API、运行时 Git 访问、知识库四条链路，某一条可用不代表其他链路可用。

## 10. 分期实施与验收

### 第一期：先跑通一个真实工单

1. 增加不改变旧语义的模块/版本/依赖和业务项目分支映射。
2. 实现工作区级 MIS 连接、工单列表/详情、整理稿和幂等转任务。
3. 实现可后绑定的专属小队与独立执行项目，缺少绑定只允许保存草稿。
4. 贯通结构化执行快照、代码准备、角色任务继承和总目录自动归档、规范复用与增量迭代。
5. 贯通老项目已有分支、新项目实际修改仓库的授权建分支和映射保存。
6. 贯通修复、独立验证、最终提交、原有 CI 跟踪、多仓库镜像汇总、组合运行环境和人工验收记录，不改历史 CI。

以“ECM V6 + 一个客户项目 + 一个依赖模块”作为试点。配置、查询和转换可以单独验证；只有真实代码检出、修复、交付及人工验收均有证据，才算闭环验收。

### 第二期：提高规模和维护效率

- GitLab 批量扫描、AI 候选映射、定时差异发现。
- 标准版本回补任务与更丰富的项目分支历史对比。
- 多仓库交付统计界面、阶段门禁与明确的验收操作完善；基本整体完成判定不推迟。
- 有实际吞吐需求后再增加产品专项成员、多小队路由和并发。

### 后续需要外部契约的部分

- MIS 修改、解决方案写回、状态关闭和附件下载所需的真实接口与权限。
- 历史产品构建环境、测试数据和不能自动化验证的业务验收条件。
- GitLab 项目分支命名、创建/push/MR 权限及发布审批规则。

缺少这些契约时保留可追踪的人工处理点，不编造接口和“自动完成”结果。

### 关键验收用例

- 没有工单小队或运行时离线时，清楚提示原因，绝不使用原开发小队。
- 工单主任务和子任务均不触发旧业务项目的开发工作流。
- 两人同时转换同一工单，只得到一个主任务；跨工作区不串单。
- 客户模块分支优先于版本基线，依赖模块独立解析；缺失分支不静默切换。
- 同一仓库多模块只检出和交付一次；不创建未修改模块的客户分支。
- 不同机器的成员能拿到一致上下文和最终代码，不依赖共享绝对路径。
- 只设置一次知识库总目录，自动按产品/版本/模块/分支归档；同分支命中复用、变化增量迭代，不按工单重复建目录，客户差异不污染标准版本，上传失败如实可见。
- 历史版本仓库和 CI 不变；各仓库镜像与依赖镜像可汇总成同一个健康可访问的测试环境，缺镜像或服务未就绪不得通过。
- 修复者不能代替独立验证，派发或 CI 成功均不能自动认定人工验收通过。
- 多仓库一失败整体不通过；新 SHA 不沿用被替代提交的通过结果。
- 没有 MIS 写回接口时，不误报外部工单已修改或关闭。
